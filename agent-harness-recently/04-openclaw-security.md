# 专题：OpenClaw 的安全问题——从技术缺陷到监管限用

> 调研日期：2026-09-16 · [返回索引](README.md)
> 一句话结论：**OpenClaw 的安全问题不是"配置没做好"，而是架构性的：
> 常驻 + 主动 + 多渠道 + 默认记忆持久化 + opt-in 沙箱 + 开放技能市场，
> 六个设计选择叠加，使间接提示注入在当前协议层无解。
> 它已经从技术问题升级为合规问题——CNCERT 已发预警，中国限制在政府系统中使用。**

---

## 0. 为什么单独立项

[agent-harness-2026-09.md](agent-harness-2026-09.md) 把 OpenClaw 归入「②类通用助理框架」，
其与编程型 harness 的三个根本差异，恰好也是三个攻击面来源：

| 设计选择 | 产品价值 | 安全代价 |
|---|---|---|
| **常驻 + heartbeat 主动巡查** | 不用你开口就干活 | 无人值守时被触发 |
| **IM 为入口**（微信/Telegram/Discord/飞书） | 随时随地可用 | **消息即注入向量** |
| **本地 MD + SQLite FTS5 记忆，默认持久化** | 跨会话记住偏好 | **单次注入可长期驻留** |
| **ClawHub 开放技能市场** | 生态爆发的根本原因 | **供应链爆炸半径巨大** |
| **26 个内置工具 + 系统特权** | 真能干活 | 一旦被控即全面失陷 |
| **沙箱 opt-in** | 上手无摩擦 | **默认不安全** |

## 1. 监管层面：CNCERT 预警与政府限用

> **中国国家互联网应急中心（CNCERT）针对该开源自托管 AI Agent 发出了安全风险警告。**

CNCERT 在其微信公众号通报中指出：

- OpenClaw（前身 Clawdbot、Moltbot）**默认安全配置本身较弱**
- 加上其为实现自主任务执行而获得的**系统特权访问权限**
- **可能被恶意攻击者利用来控制终端**

> **该警告也促使中国限制在政府系统中使用该工具。**

风险之一被明确点名：**提示注入**——嵌入在网页中的恶意指令，
可在 Agent 被诱导访问并处理该内容时导致敏感信息泄露。

→ **这是本报告中唯一一个已经从技术讨论上升到监管动作的条目。**

---

## 2. 零点击数据外泄（PromptArmor）

2026 年最受关注的攻击手法，因为它**完全不需要用户交互**。

### 2.1 机制

> Telegram、Discord 等 IM 应用的**链接预览功能**，可通过间接提示注入
> 被转化为与 OpenClaw 通信时的**数据外泄通道**。

### 2.2 完整攻击链

```
① 攻击者在 OpenClaw 预期会读取的网页/外部数据中植入恶意指令
        ↓
② Agent 处理隐藏指令，被诱导生成攻击者控制的 URL
        ↓
③ 被入侵的 Agent 把可访问的敏感数据附加到 URL 的 query 参数中
        ↓
④ 该链接在 IM 中被渲染为预览卡片 —— 【无需用户点击】自动传输至攻击者域名
```

**第 ④ 步是关键**：外泄由 IM 客户端的**标准功能**完成，不是漏洞利用。

---

## 3. 消息对象注入（Imperva）

针对多种注入向量的测试，结果显示注入指令：

- **对受害者不可见**
- **可跨越信任边界**进入已认证的用户上下文
- **触发攻击者代码执行**

叠加 OpenClaw **默认开启的记忆持久化**：

> **单一条病毒式传播的内容，就可能在未妥善沙箱化的环境中造成静默入侵。**

已负责任披露给 OpenClaw 安全团队，**在 2026.4.23 版本中发布修复**。

## 5. 根本原因：官方文档自己承认的架构缺陷

OpenClaw 官方安全文档的原话（值得完整引用）：

> **提示注入并不需要公开 DM**——即使只有你能给 bot 发消息，
> 它读取的任何不可信内容（网页搜索/抓取结果、浏览器页面、邮件、文档、附件、
> 粘贴的日志或代码）都可能携带对抗性指令；
> **内容本身就是威胁面，而不仅仅是发送者。**

技术上的不可解性：

> 攻击者把指令埋在 Agent 稍后会读取的内容里——邮件签名、日历邀请、GitHub issue、
> 待总结的网页、Discord 消息。当 Agent 摄入这些文本时，
> **注入指令与用户的真实请求落入同一个上下文窗口，
> 模型没有可靠方法区分二者。**

→ 这正是 [01-protocol-layer.md §5](01-protocol-layer.md) 指出的治理缺口：
**MCP / ACP / A2A 都没有表达"这段内容是数据不是指令"的能力。**

### ⚠️ 最危险的一个默认值

> **沙箱是可选启用的（opt-in）。若沙箱模式关闭，隐式 `host=auto` 会解析到 gateway 主机。**

## 6. 缓解措施

官方与安全厂商的共识建议：

- [ ] **不要把默认管理端口暴露到公网**
- [ ] **在容器中隔离服务**（并显式开启沙箱，不要依赖默认值）
- [ ] **不以明文存储凭据**；让密钥远离 Agent 可访问的文件系统
- [ ] **仅从可信渠道下载 skills**（ClawHub 是供应链风险面）
- [ ] 加强网络管控
- [ ] **默认将链接、附件和粘贴的指令视为敌意输入**
- [ ] 在沙箱中运行敏感工具

### 同样适用于其他 harness

这条提醒对 Claude Code / Codex 用户同等有效：

> **安装第三方资源前请先检查其权限、脚本、hooks 和服务连接——
> 很多 Claude Code 资源可以读文件、执行命令或向外部服务发送数据。**

## 7. 对选型的影响

| 判断 | 依据 |
|---|---|
| ②类常驻 agent **短期内难以进入企业核心场景** | CNCERT 预警 + 政府限用，已是合规问题 |
| 若必须用，**优先云托管分支而非本地裸跑** | ArkClaw **不暴露公网端口**；WorkBuddy **本地优先不上云** |
| **隐私优先场景**选纯本地方案 | AutoClaw 本地运行；但其易用性与文件操作是短板 |
| 编程型 harness 的沙箱层级值得重新评估 | **Codex 在内核层执行，模型无法绕过**；Claude Code 在应用层 |

## 8. 公允地说

必须同时记录对 OpenClaw 有利的事实，否则本文档就是选择性叙事：

- 它的**记忆系统设计被认为最合理**，给了用户最大的控制权
- 它的**工具调用能力（尤其浏览器控制与第三方服务集成）仍明显领先国产分支**
- 漏洞**得到了负责任披露与修复**（Imperva 的问题在 2026.4.23 修复）
- **2026.4.x 系列基本就是在系统性收拾 2 月爆红后暴露的安全问题**
- 官方文档**主动、坦率地承认了架构层面的不可解性**，这比掩盖要好

> 它的问题不是"不负责任"，而是**它想做的事情（常驻、主动、多渠道、有特权）
> 在当前的模型与协议能力下，本来就没有安全的做法。**
